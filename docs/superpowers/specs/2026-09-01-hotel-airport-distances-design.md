# Per-hotel airport distances for the profit/loss cost model

**Date:** 2026-09-01
**Status:** Approved design, ready for implementation planning

## Problem

The profit/loss cost model prices the vehicle side of a transfer from its
one-way kilometres. Today that distance is resolved per *region*: every hotel in
a pricing region shares the single `distanceKm` on its route in `src/routes.js`,
and the ledger derives leg km with a Dijkstra walk over the region graph
(`fixedRouteDistanceKm` in `admin/profit-loss-metrics.js`).

Two costs follow from that coarseness:

1. **A named hotel does not resolve at all.** When a booking's leg endpoint is
   the `hotel` placeholder rather than a named region, `fixedRouteDistanceKm`
   returns `null`, the leg is pushed to `unresolvedLegs`, and the intern is
   forced to hand-type the km. That manual step is the recurring pain this work
   removes.
2. **Region distance is an average.** A hotel at the near edge of a region and
   one at the far edge are costed identically, so the internal profit figure is
   only as accurate as the region is small.

We already know the one thing needed to fix both: every booking stores a
free-text `hotel_name` (NOT NULL, `bookings` table). If we know the driving
distance from Antalya Airport (AYT) to each indexed hotel, we can resolve the
leg from the hotel the guest actually named.

## Goal

Replace region distance with **per-hotel driving km from AYT** in the profit/loss
cost model. The customer-facing quote still comes from the region price in
`routes.js` — only the *internal cost* becomes hotel-accurate.

Non-goals: no change to customer pricing, the region graph (kept as a fallback),
or the booking form.

## Approach (decided)

- Distance role: **replace** region distance in the cost model.
- Source: **Google Maps** driving distance (Routes/Distance Matrix), not
  straight-line.
- Storage: a **separate static data file** keyed by hotel slug, regenerated by a
  script — seed rows in the index stay readable.
- Accuracy: **flag outliers against the existing region distance** and review
  only those; region distance is a ready-made coarse truth.

## Design

### 1. Data artifact — `src/hotel-distances.js`

A frozen object keyed by `hotelSlug` (the same slug `hotelIndex` uses), one entry
per indexed hotel (871 today):

```js
export const hotelDistances = Object.freeze({
  "rixos-sungate": { km: 62, place: "ChIJ…", district: "Beldibi", checked: false },
  // …
});
```

- `km` — one-way driving distance AYT → hotel, in kilometres. The **return leg
  reuses the same value**; the cost model already doubles it
  (`vehicleKm = oneWayKm * 2`), so only one number is stored.
- `place` — Google `place_id` of the matched hotel. Lets a re-run re-verify the
  same pin instead of re-geocoding and drifting to a different match.
- `district` — copied from the index row, for the outlier report and human
  sanity.
- `checked` — human-confirmed flag. Starts `false` (a research seed, mirroring
  the index's `status: draft` convention); flipped `true` once the outlier
  review confirms the row. Regeneration never overwrites a `checked: true` row.

A hotel with no confident match is written as `{ km: null, checked: false,
note: "no-match" }` — never a silent `0`, always surfaced in the report and the
guard.

### 2. Generation script — `scripts/build-hotel-distances.mjs`

Incremental by default, re-runnable, idempotent.

**Default run (fill the gaps):** iterate `hotelIndex`; process **only slugs
absent from `hotel-distances.js`, or present with `km: null`**. New hotels added
to the index later are the only ones geocoded on the next run; existing rows are
untouched. This is the job re-run after adding hotels.

**Flags:**
- `--refresh` — re-pull km for existing rows (e.g. roads changed), but never
  overwrite `checked: true` rows.
- `--only <slug>` — re-do a single hotel after a manual fix.

**Per hotel:**
1. Geocode query `"{name}, {district}, Antalya, Turkey"` via Google **Places
   Text Search** → top match `place_id` + latlng.
2. Driving km via **Routes API** (or Distance Matrix), origin AYT, destination
   hotel latlng, `mode=driving`, meters → km.
3. Merge into `hotel-distances.js`, preserving `checked: true` rows.

**Operational:**
- API key from `GOOGLE_MAPS_API_KEY` env — never committed.
- 871 hotels × (1 text-search + 1 route). Throttled/batched; within free tier;
  spend logged. Incremental runs cost only the new hotels.
- No / ambiguous match → `km: null, note: "no-match"` → review list.

**Report — `scripts/hotel-distances.report.json`:** per hotel, its km, its
region's current `routes.js` `distanceKm`, the deviation %, and the matched place
name. Any hotel deviating more than a set threshold from its region distance is
the outlier list a human checks (then sets `checked: true`).

### 3. Guard — `src/hotel-distances.test.js` (vitest)

Asserts **every `hotelIndex` slug has a `hotel-distances.js` entry with a numeric
`km`**. A missing entry or a `km: null` fails the test — a forgotten or
unresolved hotel becomes red CI, not a silent gap. Mirrors the existing
`hotel-index.test.js` slug-agreement check.

### 4. Wiring into the cost model — `admin/profit-loss-metrics.js`

In `resolveRealizedLegs`, the `oneWayKm` precedence becomes:

1. **manual** — `manual_outbound_distance_km` / `manual_return_distance_km`.
   Intern override, unchanged, highest.
2. **per-hotel (new)** — when the leg endpoint is the `hotel` placeholder,
   resolve `booking.hotel_name` to a slug and read `hotelDistances[slug].km`.
3. **region graph** — existing `fixedRouteDistanceKm(from, to)` for named-region
   legs.
4. `null` → `unresolvedLegs` → manual prompt. Unchanged.

Details:
- `hotel_name` is free text, so resolution reuses the booking form's matcher —
  `resolveHotelRegion` from `src/hotel-search.js` (alias-aware, Turkish-fold) —
  to get the hotel and its slug. No new matching logic.
- A `hotel_name` that matches nothing, or a matched hotel whose distance entry is
  `null`, **falls through to step 3** (region graph), so nothing that resolves
  today regresses.
- New `distanceSource: 'hotel'` tag alongside `manual` / `fixed` /
  `sold-transfer`, so the ledger UI can show where the km came from.
- Direction is irrelevant — the km is symmetric.

## Testing

- **Data guard** (§3): every index slug has numeric km.
- **Cost model** (`admin/profit-loss-metrics.test.js`): a leg to a `hotel`
  placeholder with a resolvable `hotel_name` uses the per-hotel km; an
  unresolvable name falls through to the region graph; a manual km still wins;
  `distanceSource` is tagged correctly.
- **Script**: dry-run/unit around the merge — incremental run skips existing
  slugs, `--refresh` re-pulls but preserves `checked: true`, `no-match` writes
  `km: null` not `0`.

## Rollout

1. Land the artifact, script, guard, and wiring together — but seed
   `hotel-distances.js` from a first full script run before the guard is enabled,
   so CI is green on merge.
2. Review the outlier report; correct pins with `--only`; set `checked: true` on
   confirmed rows.
3. Thereafter: add hotel to the index → re-run the script → review if flagged.
